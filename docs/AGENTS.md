1.  **信任内部实现**  
    不为不可能发生的场景添加错误处理、回退或验证。信任内部代码和框架保证。仅验证系统边界（用户输入）。当你能够直接更改代码时，不要使用特性标志或向后兼容的垫片。
2.  **抵制过度设计**  
    不为一次性操作创建辅助函数、工具或抽象。不要为假设的未来需求做设计。
3.  **明确与质疑**  
    明确说明假设。如果不确定，先问，不要猜。存在多种解释时，先列出解释，不要静默选择。如果有更简单的方案，要提出异议。困惑时停止，说明哪里不清楚。
4. **失败处理策略**  
    如果一种方法失败了，先诊断原因再换策略——读取错误、检查假设、尝试有针对性的修复。不要盲目重试，但也不要一失败就放弃。只有在调查后真正卡住时才向用户发送求助信号。
5. **风格一致性**  
    使用现有命名、结构、测试风格和错误处理模式。如果某个约定确实有害，要显式提出，不要静默分叉出另一套风格。  
    如果代码库中的两个既有模式互相矛盾，不要混合它们。选择其中一个，优先选择更新或测试更多的模式。解释选择原因，并把另一个模式标记为后续清理项。
6. **存量代码清理**  
    避免向后兼容的 hack，比如重命名未使用的 _vars、重新导出类型、为已删除代码添加 // removed 注释等。如果你确定某物未使用，可以完全删除它。
7. **阅读先于修改**  
    添加代码前，先阅读当前文件的 exports、直接调用方，以及明显相关的共享工具。如果不理解现有代码为什么这样组织，先问，再添加。“看起来和我无关”是危险信号。  
    一般来说，不要对未阅读的代码提议更改。如果用户询问或想要你修改某个文件，先阅读它，在建议修改之前理解现有代码。
8. **建设性质疑**  
    如果你注意到用户的请求基于误解，或发现他们询问的内容旁边有 bug，请说出来。你不仅是一个执行者，还是一个合作者——用户从你的判断中受益，而不仅仅是你的服从。
9. **预估禁忌**
    避免给出任务需要多长时间的时间估计或预测，无论是你自己的工作还是用户规划项目。关注需要做什么，而不是可能需要多久。
10. **禁止重复**
    不允许对同一元素同时使用class和id。
11. **阶段处理**
    先明确各环节的生命周期，再执行任务。
12. **测试职责分离**
    测试工作属于用户。若用户没有明确要求测试，不得以任何方式自行测试（包括但不限于运行游戏、启动测试脚本、编写测试代码、浏览器自动化验证），与**失败处理策略**冲突时，以**失败处理策略**的要求为主
13. **破坏性操作审批**
    删除/覆盖/移动文件等不可逆操作，必须同时满足:[(a) 相关任务的所有验证已完成并通过；(b) 操作清单已向用户列出并获得明确授权。]才能执行。删除永远放在流程的最后一步，验证完成前禁止任何删除。
14. **上下文知识库使用**
    context-mode 知识库按项目目录隔离且初始为空：只有通过 `ctx_batch_execute` / `ctx_index` / `ctx_fetch_and_index` 主动索引的内容（以及会话自动记忆）才能被 `ctx_search` 检索。新项目或从未索引时先用 `ctx_batch_execute` 采集并同步建立索引，再使用 `ctx_search`；不需要历史记忆的任务直接使用本地文件工具，不调用知识库工具。注意沙箱目录不同，需要用绝对路径。

# 补充规则
## 数据信任原则
- **绝对信任数据文件**：不为绝不可能为空值的地方做防御性检查
- **绝对信任浏览器API**：不处理 Promise 拒绝，不检查 API 是否存在
- **绝对信任用户输入**：不为用户操作添加验证

## 逻辑简化原则
- **函数职责单一**：每个函数只做一件事
- **直接调用**：不通过回调或事件转发简单操作

## PowerShell使用
- 在Windows环境中命令文本或操作目标包含中文字符时，严禁使用 PowerShell，改用编辑工具（Write/Edit）处理含中文的文件内容

## 编程任务工作流：
1. 理解问题：在回答问题之前，先向用户提问。请根据用户的问题进行追问，一直追问直到你有95%的信心完全理解用户的真实需求和目标时,再用一句话复述问题的核心，等待用户确认，用户没有明确之前禁止修改任何文件。
2. 头脑风暴：调用Questions向用户提出 2-3 种方案，附权衡与推荐，优先展示推荐项并解释原因。强制要求：未获用户确认方案前，不修改代码。
3. 验证代码：保证代码能正常运行，检查代码是否存在BUG，是否存在安全问题。
